# demo/ —— 演示素材

**这个文件夹是自包含的。** 拿到它（无论从仓库克隆，还是别人单独发给你），

## 2 按演示顺序的推荐用法

| 幻灯片环节 | 打开什么 | 说一句什么 |
|---|---|---|
| 擂台：同一首歌五种判断 | `arena_pk.md`（取 3–4 行）或 `classification/README.md` 的表 | 同一段音频，五个模型能给出五种答案 |
| 擂台：现场听一段 | `classification/073776_International.mp3` | 五个模型全错，各有各的错法 |
| 生成：整条链路 | `audio/README.md` 顶部说明了四段式 | 音频 → Token → 预测 → 解码 |
| 生成：现场听（重点） | `pairs/` 里同一曲目的 1→2→3→4 | 先放原曲，再放真实后续，最后放两种续写 |
| 生成：盲听 | `REAL__` / `GENbase__` / `GENft__` 改名成 A/B/C | 猜哪条是真实录音 |
| 生成：主动放负例 | `AB__001482_Electronic.mp3` | 这一条适配后反而更差，我们照样放 |
| 收尾 | `audio/README.md` 的逐曲距离表 | 指标只奖励"贴近原曲"，不等于好听 |

**只用 5 分钟的话**：`pairs/` 里 `000995` 那四条（1→2→3→4，共 63 秒）→ `classification/073776_International.mp3`
→ 逐曲距离表。其余都可以口述。

## 3 文件命名规则（看名字就知道是什么）

```
<曲目号>_<流派>__<角色>.mp3      单段素材，角色 ∈ prompt / true / base / ft
AB__<曲目号>_<流派>.mp3          四段串联：前缀 → 真实 → 原始 → 适配
REAL__ / GENbase__ / GENft__ …   无缝两段：5 秒前缀 + 对应的后 3 秒
TOK__<曲目号>_<流派>__pred.mp3   Token 预测出的 1 秒
TOK__<曲目号>_<流派>__true.mp3   同一位置的 1 秒真实音频
```

- `prompt` = 模型看到的前 5 秒；`true` = 真实的后 3 秒；`base` = 原始 MusicGen；`ft` = LoRA 适配后
- 曲目号是数据集里的原始 ID（FMA / GTZAN 各自的编号）

## 3.5 关于时长：为什么是 5 秒 / 3 秒，能不能更长

这是被问过最多的问题，答案分两半：

**分类片段（5 秒）**：改长是**免费**的——素材本身就是 30 秒。所以本目录另给了
`*_context15.mp3`（中心 15 秒）与 `FULL30__*`（整曲 30 秒）供人耳听上下文。
但**模型始终只吃中心 5 秒**，这是训练时的口径；把 30 秒说成"模型听了 30 秒"就是夸大。

**续写片段（3 秒）**：3 秒是"8 首测试曲都能稳定跑完"的口径，**不是能力上限**。
我们在其中一首上实测过更长的续写（同一段 5 秒前缀）：

| 续写长度 | 生成耗时（RTX 4060） | 峰值显存 | 情况 |
|---|---|---|---|
| 3 秒 | ≈ 5.6 秒 | 1.35 GB | 8/8 曲目稳定，主结果口径 |
| 4 秒 | 6.4 秒 | 1.36 GB | 可生成 |
| 6 秒 | 16.3 秒 | 1.38 GB | 可生成 |
| 8 秒 | 18–21 秒 | 1.42 GB | 可生成（LoRA 同样可，约 21–30 秒） |
| 12 秒 | 35.4 秒 | 1.51 GB | 可生成 |
| 16 / 20 秒 | — | — | **崩**：位置嵌入索引断言 |

崩溃点不在长度表，而在 MusicGen 的 `pad/bos token id = 2048` 超出词表（0–2047），
长序列更容易走到这条路径。所以：
- **要更长的演示音频**：用 `LONG__` 里那几条（前缀 + 8/12 秒），最长 17 秒；
- **要稳定批量出 15 秒以上**：得换生成实现（官方 `audiocraft` 支持 30 秒，但要求
  Python 3.10 + torch 2.1，与我们的环境冲突），不是改个参数的事。

`demo/audio/README.md` 里每条都标了时长与客观距离。



| 环节 | 能不能现场跑 | 怎么做 |
|---|---|---|
| 分类（五个自建/传统模型） | ✅ CPU 就够，单段 0.1–0.3 秒 | 见 `classification/README.md` 方式 2 |
| 分类（AST） | ❌ 346 MB、约 200 ms/段（GPU 口径） | 口述榜上成绩与成本对比 |
| 生成（MusicGen 续写） | ❌ 300 M 参数自回归，CPU 上一段要数分钟 | 只放 `audio/` 里已生成好的 mp3 |

所以最稳的现场方案是：**分类放 mp3 或 CPU 跑，生成只放录音。**
两者都不需要网络、不需要权重、不需要数据集。

## 5 授权与红线

- **FMA-small 片段**（`classification/`）：CC-BY 4.0，允许再分发，条件是按曲目署名——
  艺术家与曲名已列在 `classification/README.md` 的表格里。**公开使用时请保留该表。**
- **GTZAN 片段**：**不在本目录内**。GTZAN 音频版权归各权利人，项目不分发；
  `arena_pk.md` 只是预测结果的表格，不含音频。
- **生成音频**：由 MusicGen-small（CC-BY-NC 4.0）续写得到，课堂演示可用，
  **不要公开发布**（详见技术报告 §7.10）。
- 所有音频只留 1 dB 余量、**不做响度归一**：真实录音的前缀本来就比续写段落安静，
  抹平这个差异反而会让人误判哪一段是原曲。早期版本用过 `loudnorm -18 LUFS`，
  把 5 秒片段压掉约 11 dB，听感就是「前 5 秒几乎没声音」，已修。
