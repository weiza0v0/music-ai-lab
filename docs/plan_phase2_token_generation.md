# 阶段一：EnCodec Token 预测实验

## 1. 实验目标

研究 LSTM 与小型自回归 Transformer 是否能够根据音乐前缀预测原曲真实后续部分的离散音频 Token。

此阶段的核心是可控的神经网络实验，而不是直接调用完整的音乐生成模型。

## 2. Tokenizer 与数据

优先评估与 MusicGen 兼容的 EnCodec 32kHz 音频编码配置。

要求：

- 使用预训练 EnCodec 编码器将音频转为离散 Token。
- 确认输入采样率、通道数、归一化方式、码本数量、每个码本的 Token 数量、Token 帧率及张量形状。
- 检查编码器输出与解码器输入是否兼容。
- 缓存编码后的 Token，避免每轮训练重复编码。
- 记录 tokenizer 的模型版本和配置。

不要假设所有 EnCodec 检查点都能与 MusicGen 的 Token 格式互换。必须根据实际模型配置核实兼容性。

先使用少量音频跑通端到端流程，再扩大数据规模。

## 3. 数据集和切分

优先复用现有项目中合法可用的音乐数据。

要求：

- 先按歌曲或艺术家划分训练集、验证集、测试集，再构造滑动窗口。
- 同一首歌曲的相邻窗口不得分布在训练集与测试集两边。
- 如果使用 FMA-small 等数据集，保留原有 artist-disjoint 实验的划分原则。
- 如果某个数据集的音频长度、质量或许可证不适合此任务，应说明原因并选择可用的替代数据。
- 固定随机种子，保存划分清单。

初始设置建议：

- 输入前缀：5 秒
- 预测目标：接下来 1 秒
- 第一版先验证 Token 序列的完整训练、预测和解码流程
- 后续再尝试 2 秒预测

这些是初始参数，可以根据 Token 帧率和显存占用调整，但需要记录调整原因。

## 4. 模型设计

至少实现以下模型：

A. Baseline：

- Persistence / 重复最近 Token 的基线；
- 如果合理，增加简单 n-gram 或按历史频率预测的基线。

B. LSTM：

- 输入历史 Token 序列，预测未来 Token。
- 使用 Embedding、LSTM、预测头和交叉熵损失。
- 先实现单码本预测。
- 记录上下文长度、隐藏维度、层数、优化器和训练参数。

C. 小型自回归 Transformer：

- 使用 Token Embedding、位置编码、因果注意力和语言模型预测头。
- 训练时使用 next-token prediction 与交叉熵损失。
- 推理时采用自回归生成，避免使用未来真实 Token。
- 先实现单码本版本，确认可运行后再评估多码本扩展。

注意：单码本预测是简化实验，不代表已经完整建模 EnCodec 的所有音频 Token。报告中必须明确这一限制。

## 5. 训练与评估

要求：

- 训练集用于参数学习，验证集用于超参数选择，测试集仅用于最终评估。
- 采用固定随机种子，至少运行 3 个随机种子；若资源不足，先跑通再补齐。
- 记录训练损失、验证损失、最佳 checkpoint 和训练耗时。
- 使用适当的验证集早停与模型保存策略。

定量指标：

- Token Top-1 Accuracy
- Token Cross-Entropy / NLL
- 可选 Top-k Accuracy
- 推理时间与峰值显存

生成与解码：

- 将预测的未来 Token 与原曲真实 Token 分别整理为可解码格式。
- 只有在 tokenizer 的输入格式与多码本要求均满足时才尝试解码。
- 先验证单码本预测的 Token 能否合理映射到解码输入；若不兼容，明确报告限制，不得伪造音频结果。
- 若可行，解码预测 Token，并与原曲真实后半段进行试听和频谱对比。

## 6. 阶段一交付物

必须提供：

1. 可运行的数据准备、Token 编码、训练、评估和推理代码。
2. Baseline、LSTM、小型 Transformer 的对比表。
3. 训练曲线、Token 预测结果及可用的音频样例。
4. 数据划分清单和实验配置文件。
5. README：从 Conda 环境到运行实验的完整命令。
6. 对实验局限的说明，特别是单码本与多码本解码之间的差异。

阶段一验收条件：

- 从原始音频到 Token 预测指标的完整流程可以重复运行。
- LSTM 和 Transformer 均能训练、保存、加载和推理。
- Baseline 与神经网络模型使用同一测试集和同一评价规则。
- 结果可追溯，不能只报告手动挑选的成功案例。
- 若 Token 解码无法合理进行，必须如实记录，并先解决兼容性问题，再进入依赖该结果的后续工作。

完成后暂停，提交阶段一报告，等待验收后再开始阶段二。

# 阶段二：预训练音乐生成模型轻量微调

## 1. 实验目标

评估预训练音乐生成模型在音乐前缀条件下生成续写音频的能力，并比较原始预训练模型与微调后模型。

该阶段是音乐生成任务，不应与阶段一的真实未来 Token 预测混为一谈。

## 2. 候选模型

优先评估：

- `facebook/musicgen-small`

如果该模型不适合当前环境，再根据实际依赖、许可证和显存情况评估其他模型。

在选定模型前，先核实：

- 模型结构与参数量；
- 预训练检查点和许可条件；
- 音频提示 / continuation 接口；
- 训练代码是否支持所需的条件生成任务；
- 模型输入输出 Token 格式；
- 当前显存下的推理与训练可行性。

不要仅凭模型名称判断它能否直接对音频前缀进行续写，也不要默认通用 Hugging Face 接口能够完成所有训练步骤。

## 3. 先做原始模型推理

在微调之前，必须先完成最小可运行测试：

1. 加载预训练检查点。
2. 准备一段短音频前缀。
3. 使用模型支持的音频条件生成 / continuation 方法生成后续音频。
4. 保存输入、输出 WAV。
5. 测量推理耗时和 GPU 峰值显存。
6. 确认输出音频格式、采样率、声道和有效长度。
7. 检查生成结果是否包含重复提示片段，并确认续写片段的截取方式。

先使用短片段，确认模型可用后再增加生成长度。

如果原始模型在当前 GPU 上无法稳定运行，先尝试合理的显存优化或独立 CPU 回退；不得直接开始大规模微调。

## 4. 微调方案

优先考虑低成本的参数高效适配，例如 LoRA 或其他经过验证的轻量微调方式。

但必须先检查所选模型及其官方实现是否支持所计划的适配方法。若 MusicGen 的特定模块不支持直接使用 LoRA，不要强行套用；应选择官方支持的微调路径，或改为只训练可控的小型条件预测模块。

训练数据应构造为：

- 输入：音乐前缀；
- 目标：同一首歌紧接其后的真实音频 / Token 序列。

要求：

- 优先复用阶段一已经清洗并切分的数据。
- 保证训练集、验证集和测试集在歌曲或艺术家层面隔离。
- 不得将测试集用于微调、提示调参或人工挑选超参数。
- 先用小规模数据做过拟合 / 端到端检查，确认目标和 loss 正确。
- 使用较小学习率、梯度裁剪、合理的 batch size、混合精度（如兼容）和梯度累积（如必要）。
- 记录训练参数、显存峰值、训练耗时和模型 checkpoint。
- 若全量微调超出显存或时间预算，停止并切换到更轻量方案，而不是持续尝试不受控的优化。

特别注意：MusicGen 可能使用多码本音频 Token。必须沿用模型原有的 Tokenization、条件输入和训练目标，不能把阶段一的单码本简化代码直接用于完整模型微调。

## 5. 生成评估

在相同的测试前缀上，比较：

- 原始预训练模型；
- 微调后模型。

尽可能保持生成参数一致，并保存随机种子和生成配置。

评估包括：

- 生成耗时；
- 峰值显存；
- 输出音频时长；
- 人工试听的连贯性、节奏稳定性、音色一致性；
- 如条件允许，增加客观音频指标，但不得把单一客观指标解释为完整的音乐质量评价。

对原曲后半段的相似性与生成质量分别报告。模型生成的音乐不必逐 Token 等于原曲，但如果目标是续写，应检查它与输入前缀的衔接情况。

## 6. 阶段二交付物

1. 原始预训练模型的推理脚本。
2. 可复现的微调配置和训练脚本。
3. 原始模型与微调后模型的生成音频。
4. 训练损失曲线、显存与耗时报告。
5. 生成质量比较及失败案例分析。
6. README 和独立环境的依赖锁定文件。
7. 明确记录未实现的功能、技术限制和许可信息。

阶段二验收条件：

- 原始模型至少能够对一段前缀生成有效音频。
- 若微调成功，能保存并加载微调后的 checkpoint。
- 原始模型与微调后模型能在相同测试前缀下进行公平比较。
- 如果微调由于显存、依赖或官方实现限制而不可行，应提交失败原因、日志和替代方案，不得将未完成的微调描述为已完成。
