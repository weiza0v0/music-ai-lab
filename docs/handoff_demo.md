## 1 演示总纲（来自炜仔0v0 的想法，已落成可执行方案）

三个故事，一条线串起来：

| # | 故事 | 观众看到什么 | 靠什么支撑 |
|---|---|---|---|
| 1 | **擂台 PK**：六个模型同一批曲目打擂台 | 同一首歌，五个模型给出五种判断；准确率榜 + 成本榜 | `demo/arena_pk.md`、`leaderboard.png` |
| 2 | **归纳偏置**：为什么 Transformer 在小样本上输给 CRNN，预训练后却最强 | 一条「先验越少 → 越吃数据 → 预训练补上先验」的曲线 | 报告 §7.6 + 下表 |
| 3 | **预测任务**：前半段音频 → 后半段 | 放音频：前缀 → 真实 → 原始续写 → LoRA 续写 | `demo/audio/AB__*.mp3` |

分工：**判别式（故事 1+2）一段，生成式（故事 3）一段**，各 6–7 分钟，中间不断层。

一句话主轴（建议开场就说）：

> 我们想回答一个问题：**同样一份数据、同样一条纪律，模型能把音乐理解到什么程度？**
> 判别式任务给出「能分类到什么程度」，生成式任务给出「能续写到什么程度」——
> 两者指标不能互比，但纪律是同一套。

### P1 封面

- 副标题：判别式流派分类 × 生成式离散 Token 预测
- 一句话：同一份划分、同一条纪律、两种可度量性。

### P2 一个问题 → 两个任务
- 左：分类 `p(流派 | 音频)`；右：预测 `p(下一个 Token | 前 5 秒)`
- 关键事实：**两个任务用同一份 FMA-small 与同一份按艺术家分离的划分**，
  所以「分类器认对了这首歌」与「模型能续写这首歌」是对同一批曲目的两种提问。
- 数字：985 首（GTZAN，MVP）/ 7,994 首（FMA-small，主实验）/ 测试 147 与 1,199 首
- 素材：报告图 1（判别式流程）、图 2（生成式流程），或从 PDF 第 9 页截图

### P3 擂台规则（怎么比才算公平）
- 三种子、验证集选型、测试集只评一次、cuDNN 确定性
- **一条很容易被忽略的规则：按艺术家分离划分**。同样数据、同样模型，只换成按曲目划分，
  CNN 的 Macro-F1 从 0.470 跳到 0.568（+9.9），因为 81% 的测试曲与训练集共享艺术家。
- 素材：`results/gtzan/figures/confusion_matrices.png`（可选）、报告 §3.4 表 4

### P4 擂台结果：准确率榜
- 素材：`results/gtzan/figures/leaderboard.png`（GTZAN，Macro-F1 + 训练成本对数坐标）
- 素材：`results/fma/figures/leaderboard_fma.png`（FMA-small）
- 数字（Macro-F1）：GTZAN — SVM 0.699 / MLP 0.630 / CNN 0.753 / CRNN 0.723 /
  TF 0.542 / **AST 0.814**；FMA — 0.440 / 0.422 / 0.470 / **0.492** / 0.378 / **0.590**
- 一句话：**自建模型里 CNN 在 GTZAN 赢、CRNN 在 FMA 赢；但两个数据集的第一名都是 AST。**

### P5 代价榜：赢了要付多少
- 表：延迟 0.02–0.76 ms（自建） vs 204/231 ms（AST）；体积 1–2.4 MB vs 346 MB；
  训练时间 GTZAN CNN 57 s vs AST 线性头 23 s（另有 214 s embedding 提取）
- 一句话：**AST 的延迟是 CNN 的约 270 倍、体积 145 倍**——离线标注可接受，实时交互不行。
- 素材：报告 §5.4 表 + `leaderboard.png` 二次利用（对数坐标正是为这页准备的）

### P6 同一首歌，五种判断（擂台最直观的一页）
- 直接放 `demo/arena_pk.md` 第一节的表，**只取 3–4 行**
- 推荐 3 行（都在表里）：

| 曲目 | 真值 | SVM | MLP | CNN | CRNN | TF |
|---|---|---|---|---|---|---|
| `classical.00099` | classical | ✓ 82% | ✓ 100% | ✗ rock 77% | ✗ country 70% | ✗ jazz 46% |
| `hiphop.00055` | hiphop | ✗ country 32% | ✗ disco 41% | ✗ reggae 64% | ✗ reggae 33% | ✓ 92% |
| `disco.00069` | disco | ✗ rock 53% | ✗ rock 51% | ✓ 58% | ✗ blues 50% | ✗ jazz 89% |

- 讲法：**同一段音频，五个模型能给出五种答案**。注意 `classical.00099`：人工特征的两个模型
  都对，CNN 却以 77% 的自信说 rock——这就是下一页要说的事。

### P7 归纳偏置：先验越少，越吃数据
一行公式化表达即可，别堆公式：

| 模型 | 内建的假设 | 数据少时 |
|---|---|---|
| SVM / MLP | 人工特征里已经写好了先验（MFCC、节奏统计） | 稳，但天花板低 |
| CNN | **局部性 + 平移等变**：只看邻域、图案搬到哪都算同一个 | 强 |
| CRNN | CNN 的局部性 + **循环层的记忆假设**（时序状态） | 强，数据够时更强 |
| 轻量 Transformer | 只有位置编码，**几乎没有结构先验**，关系全靠数据学 | **严重过拟合** |
| AST | 同为 Transformer，但 AudioSet 预训练**把先验灌进去了** | 最强 |

- 我们自己的证据（这是这一页的分量所在）：
  - GTZAN：CNN 0.753 > CRNN 0.723 ≫ **TF 0.542**（65 万参数不到，985 首训不动）
  - FMA：**CRNN 0.492 > CNN 0.470** —— 数据够了，序列建模才开始值钱
  - AST：0.814 / 0.590 —— 同一个 Transformer 架构，**预训练后从最差变成最好**
- 结论句：**问题不在架构，在数据与先验。**

### P8 一个诚实的负结果（判别式侧）
- 正则化（SpecAugment、标签平滑）在 FMA 上最大只有 +0.7 个百分点，落在种子波动内；
  训练从 30 轮加到 60 轮，两个数据集互有胜负（GTZAN +0.75/+1.36，FMA −0.5 左右）。
- 一句话：**能调的旋钮都试过了，剩下的差距不是调参能补的。**
- 素材：报告 §5.3 表 13

### P9 转折页：分类器不知道下一秒
- 一句话：分类输出一个标签，**它没有"接下来"这个概念**。
- 办法：把音频变成**离散 Token**（EnCodec：32 kHz、4 个码本、每秒 50 帧），
  "预测音频"就变成"预测下一个符号"，可以直接用交叉熵。
- 素材：报告 §2.4 的三句话 + 图 2（生成式数据流）

### P10 生成式流程（一页讲清）
- 链条：`30 秒片段 → 32 kHz → 每首 2 个 6 秒窗（前 5 秒前缀 + 后 1 秒目标）
  → EnCodec → 4×300 Token → 预测模型 / MusicGen`
- 要点：**5 秒前缀 → 1 秒目标**（Token 预测）、**5 秒前缀 → 3 秒续写**（MusicGen）
- 素材：`results/token_prediction/figures/token_decode.png`（预测 vs 真实的频谱对照）

### P11 Token 预测：能学，但学得很少
- 数字：随机猜 0.049% → Bigram 1.71% → LSTM 2.08% → **Transformer 2.19%**（free-running）；
  teacher-forced 3.36% → free-running 2.19%，**一步就掉 35%**
- 一句话：**模型确实学到了局部动态，但绝对水平只有随机的 45 倍，远不足以写出乐句。**
- 素材：`results/token_prediction/figures/token_top1.png`、
  `token_per_codebook.png`（码本 0 最容易，越往后越难，符合 RVQ 结构）

### P12 现场听（全场重点，别赶）
- **放 `demo/audio/AB__000995_Experimental.mp3`**（16 秒，一条听完四段）：
  ① 5 秒前缀 → ② 真实后 3 秒 → ③ MusicGen 原始续写 → ④ LoRA 适配后续写
- 客观数字：这条曲目 Log-Mel RMSE 20.85 → 17.19（**−3.65**，8 首里改善最大的一首）
- 讲法：先问"哪一段是真实的"，再公布答案；**不要指望观众听出适配前后**，
  只说"客观距离上它更接近真实"。
- 素材：`demo/audio/` 全部 42 个文件，逐条说明见 `demo/audio/README.md`

### P13 负结果的负结果（生成式侧最有价值的一页）
- **主动放 `demo/audio/AB__001482_Electronic.mp3`：这一条适配后反而更差（+0.33）**，
  8 首里唯一退步的一首。
- 讲三件事：
  1. LoRA 初版完全无效，原因是**标签维度写错**——用未训练模型一测就知道：
     错误布局 loss 11.08 / 正确布局 5.46 / 均匀分布 7.62。错误布局下"比乱猜还差"，
     梯度方向本身没有意义，训多少步都不会收敛。
  2. 修正后 19.23 → 17.91（−1.32，配对检验 t=−3.36 显著，7/8 首改善）。
  3. 但再去调步数/窗口/秩，**三个旋钮全都不显著**：NLL 继续降，音频不动。
- 一句话：**"训不动"未必是容量不足，可能只是目标对齐写错了；而"指标变好"也未必是质量变好。**

### P14 结论
- 判别式：预训练是单点最大收益，但贵 270 倍；数据规模会改变模型排序；泄漏能让结论虚高 10 个点。
- 生成式：Token 级预测可复现但上限很低；误差累积是墙；LoRA 修正对齐后有可测改善，旋钮无效。
- 收尾句：**我们没有把"跑通"当成"做好"——三个负结果都留在报告里。**

## 6 归纳偏置：技术底稿（讲之前先看这段）

### 6.1 各模型的归纳偏置是什么

- **CNN：局部性 + 平移等变**。卷积核只看邻域（局部性），图案移到别处仍被同一组权重检出
  （平移等变；池化才带来近似的平移不变）。对频谱而言，"局部时频纹理"是强先验，
  所以它在千首级数据上就能训出可用结果。
- **RNN（我们的 CRNN 用 BiGRU）：记忆假设**。隐状态假设"当前输出依赖一段历史"，
  天然适合建模时间演化；代价是长程依赖难、训练慢。**它的先验比 CNN 弱一点，比
  Transformer 强得多。**
- **Transformer：几乎没有结构先验**，只有位置编码；它假设"任意两帧都可能相关"，
  关系必须从数据里学。先验少 → **样本效率低** → 小数据上过拟合；
  先验少 → **上限高** → 数据/预训练足够时反超。这两句话是同一枚硬币。
- **AST：同一个 Transformer 架构 + AudioSet 预训练**。预训练把"什么声音长什么样"
  灌进权重，等价于补上了先验，于是它从"最差的架构"变成"最强的模型"。
- **SVM / MLP：几乎没有内建先验**，但**输入的人工特征本身携带先验**（MFCC、chroma、
  节奏直方图都是人类设计的）。所以它们不是"没有先验的模型"，而是"先验前置到了特征里"。
  ——这一点答辩时容易被问到，值得准备一句。

### 6.2 我们自己的证据（三条，按顺序讲）

1. **GTZAN（985 首）**：CNN 0.753 > CRNN 0.723 ≫ 轻量 TF 0.542。
   TF 的训练损失迅速趋 0 而验证损失抬头，是标准的过拟合曲线
   （`results/gtzan/figures/training_curves.png`）。
2. **FMA-small（7,994 首）**：CRNN 0.492 > CNN 0.470。数据变多后，**CRNN 反超**——
   说明"带记忆的结构"不是没用，而是需要数据养。
3. **AST**：0.814 / 0.590，两个数据集都第一。同为 Transformer，**预训练后结论反转**。

一句话总结（可以直接当结论说）：

> 先验越少，越吃数据；数据不够时，少先验就是劣势；预训练可以把先验补回来。

### 6.3 可能被追问的三个问题

- **"为什么不用更大的 Transformer？"** → 8 GB 显存 + 千首级数据；我们做过 30 vs 60 轮
  的预算消融，加长训练没有救回小数据上的过拟合（报告 §5.3）。
- **"AST 不是更好吗，为什么还用自建模型？"** → 延迟 270 倍、体积 145 倍，实时场景用不了；
  而且它是**冻结主干 + 线性头**，不是微调，代表的是"冻结表征的线性可分性"。
- **"准确率这么低是不是模型不行？"** → FMA 的 8 个类别里有 Pop / Instrumental 这种宽标签，
  人工标注者之间也会分歧；我们在报告 §5.5 逐类分析了，Pop 的 F1 只有 0.24–0.43。

## 7 红线（说错了会被追问，务必避开）

1. **不要跨任务比数字**。Macro-F1 是"答对多少"，NLL 是"分布多接近"，Log-Mel RMSE 是
   "离真实未来多远"。三个不能并列、不能相加、不能说"生成任务比分类任务差"。
2. **不要说"用前半段预测后半段"**。我们做的是 **5 秒 → 1 秒**（Token）与 **5 秒 → 3 秒**
   （MusicGen）。说成"预测后半段 / 整曲续写"就夸大了。
3. **不要说"AI 作曲 / 生成音乐"**，说"**前缀续写**"或"局部续写"。
   而且 3 秒上限是工程限制（解码器位置索引越界），不是我们不想做长。
4. **不要拿 8 首说"提升了 7%"**。正确说法：8 首上配对检验显著，均值 −1.32 dB，
   7/8 首改善，去掉最优一首后 −0.99；**单一种子，方差未估计**。
5. **不要说"AST 微调"**，它是冻结主干 + 线性探针。
6. **不要说"所有模型在同一输入下比较"**。判别式与生成式用两条不同的前端
   （22.05 kHz 频谱 vs 32 kHz Token），同一批曲目、同一份划分，但输入不同。
7. **不要把 demo 音频公开发布**。权重与音频的许可见报告 §7.10；课堂演示可用，别上传。
8. **负结果别说成"还在优化中"**。三个负结果（正则化无效、TF 失利、噪声下崩塌）
   加上两个生成式负结果（LoRA 初版失效、去掉最优样本增益消失）都是**结论**，大胆讲。

## 8 如果你要自己跑（可选）

只需要跑演示素材的话，**不需要权重**：

```bash
git clone <仓库地址> && cd MUSIC_AI
python scripts/build_demo_bundle.py     # 若有 ffmpeg；否则直接用已提交的 demo/audio/
python scripts/build_arena_table.py     # 重新生成擂台表
```

需要真正推理（比如想自己换一段音频现场跑）时才要权重与数据，而这两者**不在仓库里**
（`data/` 23 GB、`checkpoints/` 5.9 GB，均被 `.gitignore`）。此时让炜那边跑，或按
`README.md` §2 从第 1 步重训（约 2–3 天）。

环境三条必需品（详见 `docs/repo_overview.md` §4）：
`NO_PROXY` + `no_proxy` 都要设、`NUMBA_CACHE_DIR`、`HF_HUB_OFFLINE=1`。
